# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`leash` is a single Python script (`leash.py`, executable, `#!/usr/bin/env python3` shebang) that runs a coding agent (`claude`, `codex`, ...) sandboxed with [nono](https://nono.sh), scoped to the current directory (which doesn't need to be a git repository). There is no build step and no package manager — the project is `./leash.py`, a pytest suite in `tests/` (dev-only; `leash.py` itself is stdlib-only), plus generated state under `.leash-agents/`. JSON is handled with the standard library's `json` module, so `jq` is not a dependency.

## Development

- Edit `leash.py` directly; it's the only source file. `cli` is a committed symlink to it, and it's what `install` points `~/.local/bin/leash` at; keep it. `install.sh` is the `curl ... | bash` bootstrapper from the README: after a y/n prompt (read from `/dev/tty`; no terminal means no) it clones the repo into `~/.local/share/leash` (or `git pull --ff-only`s an existing clone) and hands off to `cli install` with stdin from `/dev/tty`. Keep its logic minimal and stdlib/coreutils-only (it draws its own progress bar from `git --progress` output rather than pulling in a library); anything testable belongs in `run_install`. Every installer step that changes the system must sit behind a y/n prompt (`confirm`).
- `leash.py` requires Python 3.11+ (`MIN_PYTHON`, checked right after the imports so an old `python3`, like macOS's stock 3.9, gets a clear error). Python parses the whole file before running that check, so don't use syntax newer than 3.9 in `leash.py` (`match`, `except*`, ...); newer *library* features are fine.
- Run the tests with `uv run pytest` (pytest comes from the `dev` dependency group in `pyproject.toml`, which holds nothing but test config; `leash.py` itself stays stdlib-only). Use `-k <pattern>`, `-x`, `-m integration` / `-m "not integration"` as usual. CI (`.github/workflows/test.yml`, Linux + macOS, Python 3.11, the minimum supported version) runs `uv run --locked pytest` and also checks that `leash.py` still parses under 3.9 (see `MIN_PYTHON` above); it has no nono, so integration tests are skipped there. After changing the dev dependencies, run `uv lock` and commit `uv.lock`.
  - Tests `import leash` directly (`pythonpath = ["."]` in `pyproject.toml`); fixtures patch `leash.<name>` with `monkeypatch`. Don't name a test parameter or local `leash`: it would shadow the module.
  - `tests/conftest.py` holds the shared fixtures: `project` (a scratch project dir as a `Project` helper with `write`, `paths`, `build` → `Paths`, `profile` → parsed profile dict), `nono_cfg` (points `XDG_CONFIG_HOME` at a temp dir), and `fake_nono` (`FakeNono` patched over `leash.run_cmd`: records `nono ...` calls and pretends they succeeded; `git` calls pass through for real). Use pytest's `monkeypatch`, `tmp_path` and `capsys`, not `unittest.mock`/`contextlib`; prefer `@pytest.mark.parametrize` for table-like cases.
  - `tests/test_leash.py` (unit): every test gets `nono_cfg` and `fake_nono` (module-level `pytestmark`), so it never touches the real nono or `~/.config/nono`. Keep known bugs as `xfail(strict=True)` cases, so they fail loudly once fixed — then drop the mark.
  - `tests/test_integration.py` (marked `integration`, skipped unless `nono` is on PATH): builds profiles extending nono's built-in `default` profile (plus `claude`/`codex` when installed), checks they validate, and runs `cat`/`git` inside `nono run` to confirm what's actually readable. It never calls `main()` or `absorb_session_grants`, so it never touches the real `~/.config/nono`. Sandboxed git gets `GIT_CONFIG_GLOBAL=/dev/null` because the `default` base profile can't read `~/.gitconfig`. `test_committed_secret_leaks_through_history` asserts the documented `--with-git` leak; if it starts failing, update the docs.
- Sanity-check changes by running it against a scratch directory, both with and without `git init`: `./leash.py claude` (or any tool present on PATH with a matching nono profile).
- Syntax-check with `python3 -m py_compile leash.py`.
- `./leash.py install` symlinks `<checkout>/cli` (the checkout is found by resolving the script past any symlink) to `~/.local/bin/leash` — test install changes by running `./leash.py install` and confirming the symlink target with `readlink ~/.local/bin/leash`.

## Architecture

Everything happens in one linear script (`leash.py`):

1. **Arg dispatch** (`main`) — leading `-`-prefixed args are leash's own flags (only `--with-git`, plus `-h`/`--help`; anything else dies), so they must come before the tool name; everything after the tool name passes through to the tool untouched. The next arg is the tool name (`claude`, `codex`, ...) or the special `install` subcommand. `install` (`run_install`) first runs `ensure_nono`: offers (y/n) `brew install nono` if nono isn't on PATH and dies if declined, then for each of `NONO_PACKS` (claude, codex) whose base profile is missing (`nono profile show <tool>` fails) offers `nono pull <pack>`, and dies unless at least one profile is installed. Only then does it offer (y/n) to symlink the script itself into `~/.local/bin` (no prompt if the symlink already points at this checkout; declining stops there), and, if `~/.local/bin` isn't on `PATH`, offer (one y/n for all files) to append a guarded PATH line (`add_bin_dir_to_path`) to the startup file of the login shell (`$SHELL`) and of any other already-set-up shell (`shell_rc_files`: `.zshrc` honoring `ZDOTDIR`, `.bashrc` or `.bash_profile` on macOS, fish's `conf.d/leash.fish`), skipping files that already mention `.local/bin`. It then exits early, before any of the git/nono checks below run.
2. **Preconditions** — requires `nono`, `git`, and the target tool to be on PATH (`require_cmd`); the current directory is the project root, and it doesn't have to be a git repository.
3. **Profile generation** (`build_profile`) — turns `.leash` (gitignore syntax) into a per-project, per-tool nono profile at `.leash-agents/<tool>.profile.json`, which `extends` the tool's base nono profile. It merges two inputs: `.leash` → `filesystem.deny`, and `.leash-agents/<tool>.extra.json` (see step 5) → `filesystem.deny/allow/read/write`. `allow`/`read`/`write` entries win over a conflicting `.leash` deny for the same path (set subtraction), so a path explicitly allowed via the save-profile flow isn't left denied. Every profile also carries hardcoded protections that no `.leash` line or `extra.json` grant can undo. `ALWAYS_DENY` (`.leash`, `.leash-agents/`), plus `GIT_DENY` (`.git`) unless `--with-git` was passed, is added to `filesystem.deny`, and any allow/read/write grant on or under those paths is dropped. `.leash` and `.leash-agents/` are denied so the agent can't read or edit its own rules. `.git` is denied because a file that was ever committed can otherwise be read straight from the object database (`git show HEAD:f`, `git log -p`, zlib-decompressing `.git/objects`), and because a writable `.git/hooks` or `.git/config` would let the agent plant code that later runs unsandboxed. `GIT_COMMAND_POLICY` is written to `command_policies`: a nono tool-sandbox rule that denies every `git` invocation, so the agent gets a clear `tool-sandbox denied git` error instead of a confusing permission failure. nono also blocks running git by absolute path (verified on nono 0.79, see `test_git_by_absolute_path_is_blocked`). The `.git` deny is still needed: it stops the agent reading `.git` directly (`cat`, decompressing `.git/objects`) and backs up the command policy. The agent therefore has no git access at all inside leash, unless `--with-git` is passed (`Paths.with_git`): then `.git` isn't denied and `command_policies` is omitted, which restores git access but brings back both risks above. `build_profile` also appends `.leash-agents/` to the project's `.gitignore` (creating it if needed, via `ensure_gitignore_has_state_dir`; skipped when the project has no `.git`) — this state dir is never meant to be committed.
   - `compute_deny_paths` shells out to `git ls-files --others --ignored --directory --exclude-from=.leash` to get git's own gitignore-pattern matching (negation, `**`, anchoring) instead of reimplementing it. git runs with `--git-dir` set to **leash's own checkout** (`leash_git_dir`, resolved through the install symlink) and `--work-tree` set to the project, so the project needn't be a git repo; leash must therefore be installed via `git clone`. `GIT_INDEX_FILE` points at a nonexistent temp file so git sees an empty index: leash's own tracked files (`leash.py`, `README.md`) don't shadow same-named project files, and every project file counts as untracked. Don't add `--no-empty-directory`: combined with `--directory` it makes git drop ignored files whose parent directory isn't itself ignored (`*.env` misses `src/x.env`).
   - Profile rebuild is skipped unless the combined sha256 of `.leash`, `.leash-agents/<tool>.extra.json`, the `leash.py` script itself, and the `--with-git` mode (cached in `.leash-agents/<tool>.ignore.sha256`) has changed (`needs_rebuild`). Unrelated runs stay cheap, profiles from an older leash are regenerated after an upgrade, and toggling `--with-git` triggers a rebuild of the same profile file.
4. **Execution** — `nono run --allow-cwd --profile <generated profile> --workdir <project root> -- <tool> <args...>`, run in the foreground (via `subprocess.run`, not `exec`'d) so the script regains control afterward; the exit status is captured and re-raised at the very end, after step 5 runs.
5. **Absorbing nono's save-profile prompt** (`absorb_session_grants`) — nono's own post-session prompt (paths the agent tried to access) writes its answers to nono's *global* config keyed by a profile name — either a not-yet-applied draft (`~/.config/nono/profile-drafts/<name>.json`) or, once confirmed, a promoted user profile (`~/.config/nono/profiles/<name>.json`) — never back into this project's generated profile, so left alone those choices are silently discarded every run. `<name>` is **not reliably** the leash-generated profile name (`p.profile_name` / `leash-<tool>-<project slug>`): nono attributes a given deny rule's save-prompt to whichever profile in the extends chain actually owns that rule, so a denial coming from `<tool>`'s own base/pack profile (its default deny groups, e.g. credentials) gets saved under the plain tool name instead. `absorb_session_grants` therefore checks both names, in both locations, after each session (`absorb_from`), and folds matches back in: `$WORKDIR`-relative denies become `.leash` lines; everything else (allow/read/write, or paths outside the project) goes to `.leash-agents/<tool>.extra.json` via `append_extra`, since `.leash` can only express project-scoped denials. It then strips any `.leash` lines now covered by an allow/read/write grant (`strip_ignore_lines_covered_by_extra`), **deletes** the consumed draft or promoted file (its content now lives in the project, so leaving the global copy around would just get it silently re-absorbed every run), and calls `build_profile` immediately so the change takes effect without waiting for the next invocation.

All shell-outs (`git`, `nono`) go through `run_cmd(cmd: str, **kwargs)`, which takes a normal-looking bash command string and splits it with `shlex.split` before handing the argv to `subprocess.run` — no shell is ever invoked. Any variable dropped into one of these command strings (a path, the tool name, a user-supplied arg) is wrapped in `quote()` (`shlex.quote`) first, so values containing spaces or shell metacharacters round-trip correctly.

Key invariant: `.leash-agents/<tool>.profile.json` (and the schema/hash files alongside it) are local, disposable state (`.leash-agents/` is auto-gitignored, see step 3) — never hand-edit them or treat them as source of truth; they're regenerated from `.leash` and `.leash-agents/<tool>.extra.json`. `.leash` is the human-owned source of truth; `.leash-agents/<tool>.extra.json` is leash-owned generated state (written only by `append_extra`) for grants `.leash` can't express — it's still meant to be hand-edited when revoking a previously-absorbed grant (remove the path from its array), just not treated as authoritative the way `.leash` is.
